The signed-event agent wake path

A Kafka message wakes a headless agent. The agent streams every step back out as CloudEvents. KEDA scales the consumer from zero and back. This page walks the wire, one message at a time, and shows the event that travels on each step. Press Next for one step. Press Prev to go back. The wire box shows the messages of the current step, and the panel under it shows that step's Kafka headers and data payload. Four flows: one agent, a batch of a hundred, a forged event, and scale-to-zero as a trust control.

      Commit the Kafka offset after the terminal event, not when the message is read.
      Consumer lag then means "work not finished", not "work not read".
      KEDA scales on that lag, so the queue gauge and the agent lifetime are the same fact.
      It is structurally impossible for KEDA to remove a pod mid-run.
      One decision settles both "never miss an event" and "do not kill a running agent".

        ¹ CLI run · ² watcher run —
        two different batches. Do not pair a time
        from one with a count from the other; `agent-groups-demo.md` §Part 2 has both.
      

      

        Why 10 and not 100. The lag asks for one
        pod per pending request — ceil(100 / lagThreshold 1) = 100
        — and two ceilings cut it down:
        min(100, maxReplicaCount 10, partitions 12) = 10.
        Kafka gives each partition to exactly one consumer in a group, so pods beyond
        twelve would sit idle. Raising the cap past 12 means adding partitions first. The
        two numbers are one decision.
      

      

        10 pods is not 10 agents. Each pod runs up
        to ER_MAX_CONCURRENT = 4 turns at once, so the batch can
        run up to 40 agents at once. That is why the CLI reports 16 running against 10
        replicas.
      

      

        KEDA does 0 → 1 itself and hands 1 → N to an HPA. The Kubernetes default adds at
        most max(100%, 4 pods) per 15 s, so a burst would climb
        1 → 5 → 10 over ~30 s — half the batch. The explicit
        scaleUp policy takes the whole cap in one step instead.
      

      

        While a group is open its members' own notifications are suppressed, keyed on
        membership rather than on the group still being open — so a redelivered
        request whose duplicate terminal arrives after completion stays quiet too.
      

    


    

      
Two identities, one derivation

      

        Humans read brave-otter-4718. The agent CLI requires a
        real UUID. So both services derive the session id from the correlation id:
      

      
sessionuuid = uuid5(NAMESPACE, correlationid)

      

        No mapping table and no database read on the resume path. Both sides compute the
        same answer from the slug alone.
      

      

        Drift: spec §2.3 prints the namespace as
        …-rossoctlkeda1, which is not hexadecimal and raises
        ValueError. The code uses
        …-000000000001 (shared/ce.py:19), and the spec's own
        §6a.4 line 972 shows that correct value.
